Paradigma Basado en Recursos

¿De qué trata REST y para qué se usa?

REST es un estilo de arquitectura de software para sistemas distribuidos introducido en el año 2000 por Roy Fielding en su tesis doctoral. En lugar de ejecutar llamadas a métodos remotos, modela toda la información como recursos identificados por URIs y manipulados mediante verbos estándar del protocolo HTTP.

GET

🎯 ¿Para qué se usa principalmente?

1. APIs Públicas e Integraciones

Es el estándar universal de la web abierta (Stripe, GitHub, Twilio, Google APIs). Cualquier cliente o lenguaje con soporte HTTP puede consumir un servicio REST sin librerías adicionales.

2. Sistemas CRUD Clásicos

Gestión directa de entidades independientes: usuarios, facturas, productos, pedidos, donde las operaciones mapean de forma natural con Crear, Leer, Actualizar y Eliminar.

3. Caché de Borde y CDNs

Aprovecha la infraestructura de internet para cachear respuestas a nivel de proxy o CDN con cabeceras Cache-Control y validación ETag.

🏛️ Principios Arquitectónicos Fundamentales

1. Orientación a Recursos

Todo elemento manipulable es un recurso modelado como un sustantivo con una URI única e irrepetible. Ejemplo: /api/v1/facturas/1042 o /api/v1/usuarios/42.

2. Semántica Estricta de Verbos HTTP

Las acciones no viajan en el nombre del endpoint, sino en el verbo HTTP:

Operación CRUD Método HTTP Endpoint Ejemplo Idempotente Seguro (Safe)
Create POST /api/v1/usuarios No No
Read GET /api/v1/usuarios/42 Sí Sí
Update (Total) PUT /api/v1/usuarios/42 Sí No
Update (Parcial) PATCH /api/v1/usuarios/42 No neces. No
Delete DELETE /api/v1/usuarios/42 Sí No
3. Ausencia de Estado (Stateless)

El servidor no retiene el estado de sesión del cliente entre peticiones. Toda solicitud debe contener la información necesaria para autenticar y resolver la operación (ej. cabecera Authorization: Bearer <JWT>).

4. Formatos de Intercambio

Aunque REST es agnóstico a la representación, JSON (JavaScript Object Notation) se ha consolidado como el estándar absoluto de la industria debido a su fácil serialización y comprensión.

✅ Ventajas Técnicas

  • Caché Nativa: Reutilización directa de CDNs intermedias con códigos 304 Not Modified.
  • Universalidad: Compatible con cualquier navegador web, dispositivo o microcontrolador sin instalar SDKs.
  • Depuración Inmediata: Peticiones legibles a simple vista con curl, Postman o devtools.
  • Escalabilidad Horizontal: Al ser stateless, cualquier réplica del servicio puede atender cualquier solicitud.

⚠️ Limitaciones Arquitectónicas

  • Over-fetching: El servidor define la respuesta fija. Si una pantalla solo necesita el nombre del usuario, el endpoint devolverá igualmente 40 campos innecesarios.
  • Under-fetching (Problema N+1): Para armar una vista compleja, el cliente debe realizar múltiples peticiones secuenciales encadenadas.
  • Sobrecarga de Serialización: El formato de texto JSON repite los nombres de cada campo en cada objeto, aumentando el ancho de banda transferido.
Implementación de Código

💻 ¿Cómo se codearía una API REST para que funcione?

A continuación se muestra el código real y completo para implementar este servicio tanto en el Backend (Servidor REST) como en el Frontend (Cliente Web):

Paso 1: Implementar el Servidor en Backend (Python / FastAPI) Server Implementation 
from fastapi import FastAPI, HTTPException, status
from pydantic import BaseModel

app = FastAPI(title="API REST de Usuarios")

# Modelos de datos para validación automática
class LoginRequest(BaseModel):
    usuario: str
    password: str

# Endpoint REST: POST /api/v1/auth/login
@app.post("/api/v1/auth/login", status_code=status.HTTP_200_OK)
def login(payload: LoginRequest):
    if payload.usuario == "admin" and payload.password == "123456":
        return {
            "status": "success",
            "token": f"jwt.rest.{payload.usuario}.valid",
            "user": {"id": 1, "nombre": "Administrador", "rol": "ADMIN"}
        }
    raise HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED, 
        detail="Credenciales invalidas"
    )

# Endpoint CRUD: GET /api/v1/usuarios/{id} (Idempotente y cacheable)
@app.get("/api/v1/usuarios/{id_usuario}")
def obtener_usuario(id_usuario: int):
    return {"id": id_usuario, "nombre": "Juan Perez", "rol": "DEV_LEAD"}
Paso 2: Consumir la API desde el Frontend (JavaScript / Fetch) Client Implementation 
async function autenticarUsuarioREST(usuario, password) {
  try {
    const response = await fetch('/api/v1/auth/login', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'Accept': 'application/json'
      },
      body: JSON.stringify({ usuario, password })
    });

    if (!response.ok) {
      const errorData = await response.json();
      throw new Error(errorData.detail || 'Error de autenticación');
    }

    const data = await response.json();
    // Guardar token en memoria o almacenamiento seguro
    localStorage.setItem('auth_token', data.token);
    console.log('Sesión iniciada:', data.user.nombre);
    return data;
  } catch (err) {
    console.error('Fallo la petición REST:', err.message);
  }
}
