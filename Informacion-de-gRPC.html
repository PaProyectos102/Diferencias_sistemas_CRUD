¿De qué trata gRPC y para qué se usa?

gRPC es un framework RPC de código abierto desarrollado por Google (evolución de su protocolo interno Stubby). En lugar de enviar documentos de texto plano sobre URLs, el cliente invoca directamente funciones en el servidor remoto con serialización binaria Protocol Buffers y transporte obligatorio sobre HTTP/2.

RPC

🎯 ¿Para qué se usa principalmente?

1. Malla de Microservicios (East-West)

Estándar para la comunicación interna entre microservicios (Kubernetes, Envoy, mTLS), donde cientos de llamadas internas deben resolverse en submilisegundos.

2. Dispositivos IoT y Redes Móviles

La densidad extrema de bytes de Protobuf reduce el consumo energético del módem y la pérdida de paquetes en conexiones celulares inestables.

3. Streaming en Tiempo Real

Sistemas financieros, telemetría y pipelines de datos que requieren streaming unidireccional o bidireccional sobre un único canal TCP sin reconexiones.

🏛️ Principios Arquitectónicos Fundamentales

1. Invocación de Procedimientos Remotos (RPC)

Abandona el concepto de recursos sustantivos de REST. El cliente ejecuta funciones remotas como authService.Login(request) como si residieran en su propia memoria local.

2. Protocol Buffers (Protobuf) como IDL

Utiliza archivos .proto estrictos para definir esquemas y servicios. El compilador protoc genera stubs tipados en más de 10 lenguajes (Go, Java, Python, C++, Rust, Node.js), detectando errores de tipos en compilación.

3. Serialización Binaria (TLV + Varint LEB128)

Elimina por completo las cadenas de texto con nombres de campos. Cada dato se codifica con un tag numérico (field_number << 3) | wire_type y compresión numérica variable, ahorrando hasta un 75% frente a JSON.

4. Transporte HTTP/2 Exclusivo y Multiplexación

Múltiples llamadas viajan simultáneamente sobre una única conexión TCP sin bloqueo de cabecera (*Head-of-Line Blocking* a nivel de aplicación) y con compresión HPACK de cabeceras.

5. Trailers de gRPC-Web

El estado final de la llamada se transmite como cabeceras posteriores de remolque (grpc-status: 0 para éxito). En navegadores, gRPC-Web empaqueta estos trailers en un segundo frame con el flag 0x80.

Implementación de Código

💻 ¿Cómo se codearía gRPC para que funcione?

A continuación se muestra el código real y completo para implementar este servicio tanto en el Backend (Servidor gRPC) como en el Frontend (Cliente):

Paso 1: Definir el Contrato de Interfaz (auth.proto) IDL Estricto 
syntax = "proto3";

package auth;

// Servicio de autenticación remota
service AuthService {
  rpc Login (LoginRequest) returns (LoginResponse);
}

// Mensaje de solicitud de login
message LoginRequest {
  string usuario = 1;   // Tag: (1 << 3) | 2 = 0x0a
  string password = 2;  // Tag: (2 << 3) | 2 = 0x12
}

// Entidad de Usuario anidada
message Usuario {
  int32 id = 1;
  string nombre = 2;
  string rol = 3;
}

// Mensaje de respuesta
message LoginResponse {
  string token = 1;
  Usuario user = 2;
}
Paso 2: Implementar el Servidor en Backend (Python con gRPC) Server Implementation 
import grpc
from concurrent import futures
import auth_pb2, auth_pb2_grpc  # Archivos generados automáticamente por protoc

class AuthServiceServicer(auth_pb2_grpc.AuthServiceServicer):
    def Login(self, request, context):
        usuario = request.usuario
        password = request.password

        # Validación de credenciales en base de datos
        if usuario == "admin" and password == "123456":
            user_msg = auth_pb2.Usuario(id=1, nombre="Administrador", rol="ADMIN")
            token = f"jwt.grpc.{usuario}.valid"
            return auth_pb2.LoginResponse(token=token, user=user_msg)
        else:
            # Retornar código de error gRPC estándar (UNAUTHENTICATED = 16)
            context.abort(grpc.StatusCode.UNAUTHENTICATED, "Credenciales invalidas")

def iniciar_servidor():
    server = grpc.server(futures.ThreadPoolExecutor(max_workers=10))
    auth_pb2_grpc.add_AuthServiceServicer_to_server(AuthServiceServicer(), server)
    server.add_insecure_port('[::]:50051')
    server.start()
    print("Servidor gRPC corriendo en puerto 50051 sobre HTTP/2")
    server.wait_for_termination()
Paso 3: Consumir desde el Cliente (JavaScript / gRPC-Web) Client Implementation 
// Opción A: Con el SDK oficial de gRPC-Web
import { AuthServiceClient } from './auth_grpc_web_pb';
import { LoginRequest } from './auth_pb';

const client = new AuthServiceClient('http://localhost:8000', null, null);

async function autenticarConGrpcWeb(usuario, password) {
  const req = new LoginRequest();
  req.setUsuario(usuario);
  req.setPassword(password);

  client.login(req, {}, (err, response) => {
    if (err) {
      console.error("Error gRPC:", err.code, err.message);
      return;
    }
    console.log("Login exitoso. Token:", response.getToken());
    console.log("Usuario:", response.getUser().getNombre());
  });
}
Análisis Detallado

🔬 ¿Qué significa cada byte en gRPC-Web?

A continuación se presenta el desglose exacto de los bytes enviados en la llamada de autenticación para el usuario "admin" con contraseña "123456":

// Trama completa transmitida (Framing gRPC + Payload Protobuf):
00 Compresión
00 00 00 11 Longitud (17 B)
0a Tag 1 (Wire 2)
05 Len (5 B)
61 64 6d 69 6e "admin"
12 Tag 2 (Wire 2)
06 Len (6 B)
31 32 33 34 35 36 "123456"
1. Framing de gRPC (5 bytes)

El byte 00 indica que el payload no está comprimido. Los siguientes 4 bytes (00 00 00 11) son un entero Big-Endian de 32 bits que expresa la longitud exacta del Protobuf (17 bytes decimales).

2. Campo 1: Usuario

El byte 0a resulta de la fórmula matemática (1 << 3) | 2 (campo 1, wire type 2). Sigue la longitud (05) y los 5 caracteres UTF-8 de "admin".

3. Campo 2: Password

El byte 12 resulta de (2 << 3) | 2 (campo 2, wire type 2). Sigue la longitud (06) y los 6 caracteres ASCII de "123456".
